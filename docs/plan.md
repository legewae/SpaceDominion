### Формула ELO (мультиплеер: все N игроков играют одновременно)

Это не «попарные мини-игры», а одна игра на N участников с результатом по занятым местам:

```
N        — число игроков в матче (2..8)
place_i  — место игрока: 1 у победителя; далее по числу территорий на финише,
           при равенстве — кто выбыл позже, тот выше
S_i      = (N - place_i) / (N - 1)                  // 1.0 у победителя, 0.0 у последнего
E_i      = (1 / (N - 1)) * Σ_{j≠i} 1 / (1 + 10^((R_j - R_i) / 400))
Δ_i      = round(K * (S_i - E_i)),  K = 32
```

**Свойства, которые проверяются тестами:**
- `N = 2` → формула вырождается в классический Elo (1/0 против ожидания) — тест-эталон.
- `Σ S_i = N/2` и `Σ E_i = N/2` ⇒ в точной арифметике `Σ Δ_i = 0` (нулевая сумма).
- Остаток от округления (`|Σ Δ_i| ≤ N/2`) добавляется к дельте победителя — фиксируется в ADR-0009.
- Ничья: `Δ_i = 0` всем (по решению), независимо от формулы.
- Прерванный матч: `Δ_i = 0`, запись в историю с флагом `aborted`.
- Ожидание против «поля»: каждый игрок сравнивается со всеми остальными, а не с одним соперником.

## 2. Границы проекта

### MVP (ядро проекта, до тега `v1.0`)
- Каркас репозитория, CI, вики, ADR.
- Ядро команд: `ICommand`, `MacroCommand`, `SendCommand`, `CommandInjectable`, `Actions.Start/Stop`.
- Value objects: `Vector`, `Angle`, `Money`, `Username`, идентификаторы.
- IoC преподавателя (`App.Ioc`/`App.Scopes`) + стратегии разрешения + скоупы.
- Property-bag, репозитории, **генерируемые** адаптеры и регистрации команд.
- Шина событий + политики (event storming → код).
- Сквозные срезы: аккаунты/профили, матчмейкинг, подготовка матча, геймплей, результаты/ELO.
- Runtime: очередь команд, переключение scope, исполнение матча.
- Эмуляция серверов: пул, endpoint, маршрутизация по хэшу, перенаправление.
- Read models: лидерборд, история матчей, территории, позиции объектов.
- Вики + трассируемость «карточка → класс → тест».

### Stretch (если успеваем)
- Потоки: квант времени, HardStop/SoftStop, стресс-тест очереди.
- Более полная матрица arch-тестов.
- Сценарные тесты `MatchScenarioTests` (заменяют демо-приложение).

### Post-MVP (после v1.0; срок не жёсткий, делаем отдельными PR)
- PR-23: снапшоты матча (Memento) + периодическое сохранение.
- PR-24: миграция матча между серверами, консистентный hash-ring с rebalancing, HardStop сервера с переносом.

### Не делаем вообще
- Реальный сетевой транспорт вместо in-process эмуляции.
- Роли/админ-права.
- Персистентность в БД (только in-memory + JSON-фасад).
- Клиент/UI и консольное демо — вместо него сценарные тесты.

## 3. Архитектура (без изменений по сути)

```
Transport      : Endpoint (JSON), IMessageRouter (hash), ForwardCommand
Application    : команды, политики-обработчики, ICommandFactory, IEventBus
Domain         : value objects, агрегаты через адаптеры, правила (Strategy/Specification)
ReadModels     : проекции (лидерборд, история, территории, позиции)
Infrastructure : App.Ioc, генераторы, репозитории, очередь, scope, планировщик, пул серверов
```

Поток: `JSON → ICommandFactory → IMessageRouter → MatchCommandQueue → ThreadRunner (квант) → CommandExecutor → команда (guard → изменение через адаптер) → IEventBus → политики → новые команды`.

Скоупы: `RootScope` (аккаунты, юзернеймы, матчмейкинг, лидерборд, история, пул, часы) + `MatchScope` на матч.

`ICommand : App.ICommand` — один интерфейс на домен и контейнер.

**Правила, которые защищаются arch-тестами:**
1. `new` — только в стратегиях/регистрациях/фабриках.
2. `App.Ioc` — только в `Composition`, `Registration`, сгенерированных типах.
3. Все реализации доменных интерфейсов — только из `AdapterGenerator`.
4. В домене нет `DateTime.Now`, `Thread.Sleep`, `static`-мутабельного состояния.

## 6. Паттерны и SOLID (сокращённо, полная таблица — в `docs/patterns.md`)

| Паттерн | Где | Зачем |
|---|---|---|
| Command | все команды | запрос как объект: очередь, лог, макрокоманды |
| Composite | `MacroCommand` | подготовка матча = композиция |
| Adapter | генерируемые адаптеры | property-bag → типизированный интерфейс |
| Strategy | IoC-стратегии, `IOpponentSelector`, `IEloCalculator` | правила меняются без правки клиента |
| Observer | `IEventBus` + политики | команда не знает, кто реагирует |
| State | `MatchStateMachine` | конечный автомат вместо флагов |
| Template Method | `AbstractCommand.Execute()` = guard → apply → publish | единый каркас команды |
| Decorator | `CommandExecutor`, `RetryCommand`, `LoggingCommand` | сквозные concerns вне домена |
| Builder | `GameFieldBuilder` | пошаговая сборка поля |
| Prototype | `FieldTemplate.Clone()` | копирование конфигурации |
| Bridge | `IMatchStore` (in-memory/JSON) | смена поведения без правки клиента |
| Facade | `ServerFacade`, `PersistenceFacade` | изоляция от пула/JSON |
| Memento | `MatchResult`/снапшот (backlog) | восстановление состояния |
| Singleton (стратегия) | `SingletonRegistration` | один объект на scope |

**SOLID:** SRP — одна команда = одно изменение; OCP — новая команда/политика = новый класс; LSP — любая реализация `ICommand`/`IEventHandler`/`IEloCalculator`; ISP — узкие интерфейсы; DIP — домен на абстракциях, IoC на границе.

## 10. Статус решений и что дальше

Все ранее открытые вопросы закрыты:

- K = 32; мультиплеерная формула по местам (см. §1), ничья и прерывание — 0.
- Захват: при равенстве кораблей в клетке захвата нет.

- Срок не жёсткий: сначала MVP (PR-01…PR-22), затем post-MVP (PR-23 снапшоты, PR-24 миграция).
- Консольного демо нет: полноту сценария закрывают тесты.

**Единственное решение, которое я принимаю сам и фиксирую в ADR-0009:** нормализация остатка округления ELO — остаток `Σ Δ_i` добавляется к дельте победителя, чтобы сумма изменений была ровно нулевой. Если хотите иначе (например, не нормализовать вовсе) — скажите, поправлю ADR.
